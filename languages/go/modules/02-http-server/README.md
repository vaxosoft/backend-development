# 02. HTTP Server in Go

> Estimated time: 2h | Difficulty: Intermediate | Prerequisites: 01

## Learning Outcomes
After this module you can:
- [ ] Route requests with Go 1.22+ `ServeMux` patterns (methods, wildcards, `{$}`) and read path/query parameters
- [ ] Write middleware as `func(http.Handler) http.Handler` and chain it in the right order
- [ ] Parse forms and stream multipart uploads with a size limit
- [ ] Write responses correctly: headers before body, status codes, cookies, CORS, streaming, static files
- [ ] Configure server timeouts and shut down gracefully on SIGINT/SIGTERM

## 1. Concept Overview
An HTTP server maps *(method, path)* to a handler that reads a request (headers, query, body) and writes a response (status, headers, body). Around handlers sit cross-cutting concerns (request IDs, logging, panic recovery, CORS) implemented as **middleware**. A production server also needs **timeouts** (so slow or malicious clients cannot hold connections forever) and **graceful shutdown** (finish in-flight requests, refuse new ones, then exit).

```
client -> [RequestID] -> [Logging] -> [Recover] -> mux -> handler
                                                        <- response flows back out
```

## 2. How Go Approaches It
| Concern | Go idiom |
|---------|----------|
| Handler | `http.Handler` (one method `ServeHTTP`) or `http.HandlerFunc(func(w, r))` |
| Routing | `http.ServeMux` patterns: `"GET /tasks/{id}"`, `"/files/{path...}"`, `"GET /{$}"`; `r.PathValue("id")` |
| Method mismatch / unknown path | the mux answers `405` + `Allow` / `404` for you |
| Middleware | `func(http.Handler) http.Handler`; request-scoped data goes in `context` |
| Request data | `r.URL.Query()`, `r.Header`, `r.ParseForm`, `r.MultipartReader`, `r.Cookie` |
| Limits | `http.MaxBytesReader(w, r.Body, n)` -> `*http.MaxBytesError` |
| Response | `w.Header()` first, then `w.WriteHeader(code)`, then `w.Write`; `http.NewResponseController(w).Flush()` |
| Static files | `http.FileServerFS(fs)` + `embed.FS` + `http.StripPrefix` |
| Server | `http.Server{...Timeouts}`, `Serve(ln)`, `Shutdown(ctx)` |
| Signals | `signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)` |

No router library is needed since Go 1.22; chi/gin are intentionally not used. Non-idiomatic: `http.ListenAndServe` in production (no timeouts, no shutdown), global mutable state in handlers, a framework "context" object instead of `context.Context`.

All commands run from `languages/go/`. Every server example listens on `ADDR` (default `127.0.0.1:8080`) and exits cleanly on Ctrl-C/SIGTERM; the outputs below were produced with `ADDR=127.0.0.1:20000` (curl uses `-s -w '[%{http_code}]\n'` to print the status).

## 3. Guided Examples

### 3.1 Routing with ServeMux
- **Goal:** method + wildcard patterns, path and query parameters, `return` after `http.Error`.
- **Run:** `ADDR=127.0.0.1:20000 go run ./modules/02-http-server/examples/01_hello_mux`
- **Code:** [examples/01_hello_mux/main.go](examples/01_hello_mux/main.go)
  ```go
  mux.HandleFunc("GET /hello/{name}", hello)
  mux.HandleFunc("GET /files/{path...}", ...)
  n, err := strconv.Atoi(r.PathValue("id"))
  ```
- **Walkthrough:** `GET /{$}` matches only `/`. The mux gives `404` for unknown paths and `405` (with `Allow: GET, HEAD`) for a wrong method. `http.Error` writes the reply but does **not** stop your function, so `return` right after it. The server struct sets `ReadHeaderTimeout`, and `main` shuts down on a signal.
- **Expected output:**
  ```
  $ curl -s -w '[%{http_code}]\n' localhost:20000/hello/Ada
  Hello, Ada!
  [200]
  $ curl ... '/search?q=docs&tag=a&tag=b&limit=3'
  q="docs" tags=[a b] limit=3
  [200]
  $ curl ... '/search?limit=x'
  limit must be a positive integer
  [400]
  $ curl ... /tasks/42        ->  task 42           [200]
  $ curl ... /tasks/abc       ->  task id must be a number   [400]
  $ curl ... /files/a/b/c.txt ->  file "a/b/c.txt" (3 segments)   [200]
  $ curl ... /nope            ->  404 page not found   [404]
  $ curl ... -X POST /hello   ->  Method Not Allowed   [405]
  ```

### 3.2 Middleware
- **Goal:** request ID, logging with the status code, panic recovery, and `Chain`.
- **Run:** `ADDR=127.0.0.1:20000 go run ./modules/02-http-server/examples/02_middleware`
- **Code:** [examples/02_middleware/main.go](examples/02_middleware/main.go)
  ```go
  return Chain(mux, RequestID, Logging, Recover) // first = outermost
  ```
- **Walkthrough:** `Logging` wraps the `ResponseWriter` in `statusRecorder` to capture the code (and implements `Unwrap` so `http.ResponseController` still works). `Logging` sits outside `Recover`, so a recovered panic is logged as `500`. A panic with `http.ErrAbortHandler` is re-panicked on purpose. Request IDs generated by the server are random, so the demo sends its own.
- **Expected output:**
  ```
  $ curl -si -H 'X-Request-ID: demo-1' localhost:20000/hello
  HTTP/1.1 200 OK
  X-Request-Id: demo-1
  Content-Length: 22
  Content-Type: text/plain; charset=utf-8

  hello, request demo-1

  $ curl -si -H 'X-Request-ID: demo-2' localhost:20000/panic
  HTTP/1.1 500 Internal Server Error
  Content-Type: application/json
  X-Request-Id: demo-2
  Content-Length: 64

  {"error":{"code":"internal","message":"internal server error"}}
  ```
  Server log (stderr):
  ```
  listening on 127.0.0.1:20000
  id=demo-1 GET /hello -> 200
  id=demo-2 panic: boom
  id=demo-2 GET /panic -> 500
  bye
  ```

### 3.3 Forms and uploads
- **Goal:** URL-encoded forms, streamed multipart, `MaxBytesReader`.
- **Run:** `ADDR=127.0.0.1:20000 go run ./modules/02-http-server/examples/03_forms_uploads`
- **Code:** [examples/03_forms_uploads/main.go](examples/03_forms_uploads/main.go)
  ```go
  r.Body = http.MaxBytesReader(w, r.Body, maxUpload)
  mr, _ := r.MultipartReader()      // streams; ParseMultipartForm buffers
  n, err := io.Copy(h, part)        // hash while reading
  var tooBig *http.MaxBytesError    // -> 413
  ```
- **Walkthrough:** the upload is hashed as it streams, so memory stays flat. The client file name is reduced with `filepath.Base` and never used as a path. Going over the limit surfaces as `*http.MaxBytesError` during the read, which becomes `413`.
- **Expected output:**
  ```
  $ curl -s -w '[%{http_code}]\n' -d 'title=Write docs&tag=docs&tag=p1' localhost:20000/form
  title="Write docs" tags=["docs" "p1"]
  [200]
  $ printf 'hello\n' | curl -s -w '[%{http_code}]\n' -F 'note=ignored' -F 'file=@-;filename=../../notes.txt' localhost:20000/upload
  [{"name":"notes.txt","size":6,"sha256":"5891b5b522d5df086d0ff0b110fbd9d21bb4fc7163af34d08286a2e846f6be03"}]
  [201]
  $ head -c 2000000 /dev/zero | curl -s -w '[%{http_code}]\n' -F 'file=@-;filename=big.bin' localhost:20000/upload
  upload exceeds 1048576 bytes
  [413]
  $ curl -s -w '[%{http_code}]\n' -d 'x=1' localhost:20000/upload
  expected multipart/form-data
  [400]
  ```

### 3.4 Writing responses
- **Goal:** header/body order, negotiation, cookies, CORS preflight, streaming, embedded static files.
- **Run:** `ADDR=127.0.0.1:20000 go run ./modules/02-http-server/examples/04_responses`
- **Code:** [examples/04_responses/main.go](examples/04_responses/main.go)
  ```go
  w.Header().Set("Location", "/tasks/1")  // before WriteHeader/Write
  w.WriteHeader(http.StatusCreated)
  http.SetCookie(w, &http.Cookie{Name: "session", HttpOnly: true, Secure: true, SameSite: http.SameSiteLaxMode})
  ```
- **Walkthrough:** changing headers after `WriteHeader` is silently ignored (`X-Too-Late` never appears). `Vary: Accept` tells caches the body depends on the `Accept` header. The CORS middleware only answers a known origin and handles preflight `OPTIONS` itself with `204`. `/stream` flushes each chunk with `ResponseController`.
- **Expected output:**
  ```
  $ curl -si localhost:20000/status            # JSON (default)
  HTTP/1.1 200 OK
  Content-Type: application/json
  Vary: Accept
  Content-Length: 16

  {"status":"ok"}
  $ curl -si -H 'Accept: text/plain' localhost:20000/status    -> status: ok   (text/plain)
  $ curl -si -X POST localhost:20000/tasks     -> 201 Created, Location: /tasks/1, {"id":1}
  $ curl -si localhost:20000/login
  Set-Cookie: session=abc123; Path=/; Max-Age=3600; HttpOnly; Secure; SameSite=Lax
  $ curl -s localhost:20000/whoami             -> no session [401]
  $ curl -s -H 'Cookie: session=abc123' localhost:20000/whoami   -> session=abc123
  $ curl -sN localhost:20000/stream
  chunk 1
  chunk 2
  chunk 3
  $ curl -s localhost:20000/static/hello.txt   -> Hello from an embedded static file.
  $ curl -si -X OPTIONS -H 'Origin: http://localhost:3000' -H 'Access-Control-Request-Method: POST' localhost:20000/tasks
  HTTP/1.1 204 No Content
  Access-Control-Allow-Headers: Content-Type, Authorization
  Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE
  Access-Control-Allow-Origin: http://localhost:3000
  Access-Control-Max-Age: 600
  Vary: Origin
  ```

### 3.5 Task Tracker server with graceful shutdown
- **Goal:** everything together: JSON handlers, middleware, timeouts, `run(ctx, ln, handler, grace)`.
- **Run:** `ADDR=127.0.0.1:20000 go run ./modules/02-http-server/examples/05_tasks_server`
- **Code:** [examples/05_tasks_server/main.go](examples/05_tasks_server/main.go)
  ```go
  ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
  ...
  srv.Shutdown(shutdownCtx) // stop accepting, wait for in-flight requests
  ```
- **Walkthrough:** `run` serves in a goroutine and waits for `ctx.Done()`. `Shutdown` closes the listener at once and waits for active requests, bounded by `grace`. Request contexts are *not* derived from the signal context, so in-flight work is not cancelled. The error envelope here is simplified; module 03 does it properly.
- **Expected output:**
  ```
  $ curl -si -X POST -d '{"title":"Write docs"}' localhost:20000/tasks
  HTTP/1.1 201 Created
  Content-Type: application/json
  Location: /tasks/1
  Content-Length: 46

  {"id":1,"title":"Write docs","status":"todo"}
  $ curl -s localhost:20000/tasks/9          -> {"error":{"code":"not_found","message":"task not found"}}  [404]
  $ curl -s -X POST -d '{"title":' .../tasks -> {"error":{"code":"bad_request","message":"malformed JSON body"}}  [400]
  $ curl -s -X POST -d '{"title":" "}' .../tasks -> {"error":{"code":"validation_failed","message":"title is required"}}  [422]
  ```
  Shutdown: start `curl 'localhost:20000/slow?ms=1500'`, then send SIGTERM (Ctrl-C) 0.3 s later. A new request is refused while the slow one still completes:
  ```
  $ curl -s -w '[%{http_code}]\n' localhost:20000/healthz    # during shutdown
  [000]                                                       # curl exit 7: connection refused
  $ (the slow request)  ->  done  [200]
  ```
  Server log:
  ```
  listening on 127.0.0.1:20000
  shutting down: draining in-flight requests
  GET /slow -> 200
  stopped
  ```

## 4. Common Pitfalls
| Mistake | Why it happens | Fix |
|---------|----------------|-----|
| `http.ListenAndServe(addr, h)` in production | the default server has no timeouts: slow clients (Slowloris) hold connections forever | build an `http.Server` with `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout` |
| Handler keeps running after `http.Error` | `http.Error` only writes; it is not `return` | `http.Error(...); return` |
| `w.Header().Set(...)` has no effect | headers are frozen at the first `Write`/`WriteHeader` | set headers first; `WriteHeader` once (`superfluous WriteHeader` log) |
| `mux.HandleFunc("/", ...)` answers everything | `/` is a catch-all subtree pattern | `GET /{$}` for exactly the root |
| Unbounded request bodies | `r.Body` reads until the client stops | `http.MaxBytesReader`, then check for `*http.MaxBytesError` -> 413 |
| `ParseMultipartForm` on big uploads | it buffers parts (memory, then temp files) | `MultipartReader` and `io.Copy` to the destination |
| Using the client filename as a path | `../../etc/passwd` in `filename=` | `filepath.Base` and generate your own storage name |
| Shutdown cancels requests or hangs | deriving the drain context from the already-cancelled signal context; no grace limit | `context.WithTimeout(context.Background(), grace)`; call `Shutdown`, not `Close` |
| Treating `http.ErrServerClosed` as a failure | `Serve`/`ListenAndServe` always return non-nil, even after a clean `Shutdown` | `errors.Is(err, http.ErrServerClosed)` -> success |
| Wrapped `ResponseWriter` loses `Flusher` | the wrapper type does not implement `Flush` | implement `Unwrap() http.ResponseWriter` and use `http.NewResponseController` |
| `recover()` swallows `http.ErrAbortHandler` | middleware recovers every panic | re-panic that sentinel |

## 5. Coming From Other Languages
- **Express / Flask / FastAPI:** the mux plus middleware replaces the framework; there is no auto-binding of body to parameters (see modules 03/04). The handler gets `(w, r)` and writes explicitly.
- **Spring / ASP.NET:** no annotations or DI container: wire dependencies by closing over them or with a struct holding them (`s.list` is a method value). Middleware is `func(http.Handler) http.Handler` instead of filters/pipeline `Use`.
- **Rust (axum):** same shape (`Router` + `tower` layers) but handlers are plain functions over `http.Handler`; concurrency is a goroutine per connection, no async colouring.
- **Node:** one goroutine per request; blocking calls are fine, and cancellation travels in `r.Context()`.

## 7. Recap
- A handler is `ServeHTTP(w, r)`; the mux patterns carry the method, so you rarely need your own method checks.
- Middleware wraps handlers; order matters (outermost first), and wrapped writers need `Unwrap`.
- Always set timeouts and limit body sizes; stream large bodies instead of buffering.
- Headers first, then status, then body; return after writing an error.
- Reach for `http.Server` + `Shutdown` + `signal.NotifyContext` for anything that is not a throwaway script.

## 8. Self-check Questions
1. Why does `mux.HandleFunc("/", h)` also answer `GET /anything`, and which pattern restricts it to the root?
2. In `Chain(mux, A, B, C)`, which middleware sees the request first, and which sees the response last? Where would you put `Recover` relative to `Logging`, and why?
3. What goes wrong if the drain context for `Shutdown` is derived from the context that was just cancelled by SIGTERM?
4. Why is `r.MultipartReader()` preferable to `r.ParseMultipartForm` for a file-upload endpoint?
5. A client sends `Content-Length: 5000000` to an endpoint wrapped in `MaxBytesReader(w, r.Body, 1<<20)`. At what point does your code learn about it, and how should it respond?
